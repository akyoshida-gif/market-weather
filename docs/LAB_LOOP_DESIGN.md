# 自己改善ループの設計（案）

状態：案（2026-11-13）。オーナーの確認後に実装する。

## 1. 目的

オーナーの指示は次のとおり。

- 常に分析し続け、効かなくなった武器は外し、新しい武器を足す（2026-11-09）
- 理由は要らない。数字で勝てればよい
- 1つの手法に固執しない

参考にしたのは、高頻度取引 Bot の自己改善の記事（@supermomonga、2026-11-11）。記事では、AI を30分ごとに起こし、仮説・検証・記録を回し、6時間ごとに確定した発見を清書している。

私たちは数日〜数週間の売買なので、次のように合わせる。

- 起こす間隔：毎日1回と、週1回
- 判断の材料：本番の売買が少ないので、主に過去データでの実験を使う。デモの成績は、効かなくなったかの監視に使う
- 本番への反映：PR を作り、マージのルール（CLAUDE.md・ADR-0021）に従う

## 2. 全体の形：考える役と計算する役を分ける

| 役 | どこで | 何をするか | 持たせないもの |
|---|---|---|---|
| **考える役** | Claude のクラウドの定期実行（Scheduled tasks） | 記録を読み、仮説を立て、実験の設定を書き、計算を頼み、結果を読み、記録とPRを書く | **R2 の鍵**（秘密情報は Claude に見せない） |
| **計算する役** | GitHub Actions（新しいワークフロー `lab.yml`） | 実験の設定に従い、データを読んで計算し、結果を成果物として返す | main への書き込み権限 |
| **知識の置き場** | リポジトリの `docs/lab/` | 実験メモ・確定した発見・仮説の待ち行列・実験の通し番号 | — |

R2 の鍵は、今と同じく GitHub の Secrets にだけ置く。クラウドの Claude は、計算を頼み（ワークフローの起動）、結果（成果物）を受け取るだけにする。

## 3. 知識の置き場（`docs/lab/`）

- `queue.md`：仮説の待ち行列。優先度・出どころ・状態を書く
- `experiments/YYYY-MM-DD-<短い名前>.md`：1回の実験に1つ。次を書く
  - 仮説
  - 設定
  - 結果：探す期間、確かめる期間、年ごとの成績
  - 判定：採用、保留、却下
  - 次の一手
- `findings.md`：確定した発見だけ。週1回の清書で、実験メモから移す
- `counter.json`：これまでに試した実験の数。たくさん試すほど偶然の当たりが出るので、合格の基準を上げるのに使う

## 4. 毎日の流れ（米国の引け後、デモの実行が終わった後。例：日本時間 9時07分）

1. **読む**：前日のデモの成績、ダッシュボードの数字、待ち行列、直近の実験メモ、確定した発見
2. **監視する**：デモの各型の成績が、検証のときの成績から外れていないかを見る（例：直近30回の平均Rが、検証のときの下限を下回った）。外れていれば、その型を外すか、量を減らす PR を作る
3. **実験する**：待ち行列から1〜2個を選び、実験の設定を書く。`lab.yml` を起動し、終わるのを待ち、結果を受け取る
4. **記録する**：実験メモを書き、待ち行列を更新し、実験の通し番号を増やす
5. **採用する**：合格した型は、デモの候補（tier: candidate）に足す PR を作る。マージのルールに従う

1日の上限：実験は3つまで、`lab.yml` の実行は合計90分まで。

## 5. 週1回の流れ（日曜）

- 1週間の実験メモを読み、確かな結論だけを `findings.md` に移す
- 仮説の待ち行列を並べ直す（効いた方向を深掘りし、効かない方向は止める）
- オーナー向けの週報を書く：何を試し、何が分かり、デモの何を変えたか（`docs/lab/weekly/YYYY-WW.md`。ダッシュボードにも載せる）

## 6. 計算する役（`lab.yml`）の決まり

- 入力：実験の設定（YAML）のパスと、ブランチ名
- 実験の種類は、まず決まった型に限る。新しい種類の計算は、コードの PR としてレビューとマージを通してから使えるようにする
  - 状態の表の探索
  - 型の数値を変えた検証
  - 避ける条件の検証
  - 機械学習の時期ずらし検証
- 出力：結果の JSON と Markdown を、Actions の成果物として返す
- 権限：`contents: read`。R2 は**読み取り専用の鍵**で読む（新しい鍵が必要）
- 2024年7月以降（最後まで見ない期間）は、オーナーの承認なしには使わない

## 7. 守ること

- 予測の記録簿・時点のルール・昇格の基準・DESIGN.md の原則は触らない（CLAUDE.md）
- マージは CLAUDE.md のルールに従う。ルール自体や CI を変える PR は作らない
- 実験の数を数え、試した数が増えるほど基準を上げる（DESIGN.md 13.5）
- 秘密情報は扱わない。データを消さない
- 判断に迷ったら、実行せずに週報に「オーナーに確認したいこと」として書く

## 8. オーナーにお願いする準備

1. **GitHub との接続**：claude.ai/code の設定から、Claude GitHub App を market-weather にインストールする
2. **実行環境の作成**：claude.ai/code の環境設定で専用の環境を作る（ネットワークは Limited、パッケージの取得を許可）。設定の中身はこちらで用意する
3. **R2 の読み取り専用の鍵**：Cloudflare で、このバケットを読むだけの鍵を作り、GitHub の Secrets に `R2_READ_ACCESS_KEY_ID` / `R2_READ_SECRET_ACCESS_KEY` として登録する
4. **費用の確認**
   - Claude：今のサブスクリプションの利用枠を使う（追加の料金はない見込み）
   - GitHub Actions：このリポジトリは公開なので、標準の実行環境は無料（2026-11-13 確認）。1日90分を足しても費用は増えない
   - 公開なので、実験メモや週報も誰でも読める。売買の具体的な条件を公開したくない場合は、実験メモの置き場を R2 に移すか、リポジトリを非公開にする（非公開にすると Actions は月2,000分までの無料枠になり、今の使い方（1週間で約450分）に実験を足すと超える可能性がある）
5. **定期実行の登録**：準備ができたら、Claude Code の `/schedule` で、毎日と週1回の2つを登録する

## 9. 段階的に始める

1. まず `lab.yml` と `docs/lab/` を作り、私（この会話の Claude）が手で回して、形を確かめる
2. 次に、毎日の流れを定期実行に載せる。最初の2週間は、採用の PR を作るだけにして、マージはしない
3. 問題がなければ、マージのルールに従ってマージまで任せる
